# AGENTS.md — Karasu Buyers Club

**نسخه سند:** 1.0.0
**مخاطب این فایل:** هر عامل هوش مصنوعی (Claude Code یا مشابه) که روی این مخزن کد کار می‌کنه.

این فایل **قوانین عملیاتی الزام‌آور** برای هر تغییر در این پروژه‌ست. نادیده گرفتن هرکدوم از این قوانین یعنی تغییر باید rollback و دوباره انجام بشه.

---

## ۱. قانون شروع: چک کامل پوشه `docs/` قبل از هر توسعه

پیش از نوشتن حتی یک خط کد، عامل **موظف** است:
1. تمام فایل‌های داخل `docs/` رو بخونه: `PRD.md`, `ARCHITECTURE.md`, `GUIDELINES.md`, `ROADMAP.md`, `DEBUG_LOG.md`, `AGENTS.md`, `tasks.md`, `implementation-plan.md`
2. مطمئن بشه فاز جاری (طبق ROADMAP.md) و تسک‌های باز (طبق tasks.md) رو درست فهمیده
3. `DEBUG_LOG.md` رو مرور کنه تا مشکلات قبلی مشابه رو تکرار نکنه
4. اگه هرکدوم از فایل‌های docs وجود نداشت یا ناقص بود، اول باید تکمیل بشه، نه اینکه نادیده گرفته بشه

**این چک باید در ابتدای هر session/تسک جدید تکرار بشه — نه فقط یک‌بار در ابتدای پروژه.**

---

## ۲. ثبت تسک‌ها — `docs/tasks.md`

- هر واحد کاری قابل‌تفکیک (Feature، باگ‌فیکس، Refactor) باید قبل از شروع در `docs/tasks.md` به‌صورت چک‌لیست ثبت بشه:
  ```markdown
  ## فاز X — عنوان فاز
  - [ ] تسک ۱: توضیح کوتاه
  - [ ] تسک ۲: توضیح کوتاه
  - [x] تسک ۳: انجام‌شده (تاریخ تکمیل)
  ```
- تسک‌ها باید به همون فازبندی `ROADMAP.md` ارجاع بدن
- هیچ تسکی «انجام‌شده» علامت زده نمی‌شه مگر اینکه واقعاً تست شده و کار کنه
- تسک‌های جدید که حین کار کشف می‌شن (مثلاً یک باگ جانبی) باید فوراً به لیست اضافه بشن، نه اینکه فراموش بشن

---

## ۳. برنامه‌ریزی فاز — `docs/implementation-plan.md`

- قبل از شروع **هر فاز** از ROADMAP.md، عامل باید یک بخش جدید در `docs/implementation-plan.md` بنویسه شامل:
  - هدف فاز (خلاصه از ROADMAP.md)
  - لیست فایل‌هایی که قراره ساخته/تغییر داده بشن
  - ترتیب پیاده‌سازی (چه چیزی اول، چه چیزی بعد، و چرا)
  - ریسک‌ها یا نقاط مبهمی که نیاز به تصمیم دارن
- این برنامه باید **قبل از نوشتن کد** ثبت بشه، نه بعد از اتمام کار به‌عنوان مستندسازی گذشته‌نگر
- در پایان فاز، بخش مربوطه با خلاصه نتیجه واقعی (چه چیزی طبق برنامه بود، چه چیزی تغییر کرد و چرا) تکمیل می‌شه

---

## ۴. اعتبارسنجی قوانین (Rule-Check) قبل از هر Commit

پیش از هر commit، عامل باید تأیید کنه:
- [ ] کد مطابق `GUIDELINES.md` (Sanitization/Escaping/Nonce/Capability/Naming با پیشوند `kbc_`) هست
- [ ] `phpcs` (WPCS ruleset) بدون خطا اجرا شده
- [ ] `eslint`/`prettier` روی فایل‌های React بدون خطا اجرا شده
- [ ] هیچ Kill-switch، تله‌متری پنهان، یا اتصال بیرونی غیرشفاف اضافه نشده (طبق محدودیت‌های PRD.md)
- [ ] مستندات مرتبط (ARCHITECTURE.md در صورت تغییر ساختار، DEBUG_LOG.md در صورت رفع باگ) به‌روزرسانی شدن

---

## ۵. کنترل نسخه افزونه (Version Control داخلی)

- افزونه باید یک شماره نسخه معتبر Semantic Versioning (`MAJOR.MINOR.PATCH`) داشته باشه
- نسخه هم‌زمان در این مکان‌ها باید یکسان باشه:
  - Header فایل اصلی `karasu-buyers-club.php` (`Version: x.y.z`)
  - ثابت PHP داخلی (مثلاً `KBC_VERSION`)
  - `package.json`
  - `composer.json`
- قانون بامپ نسخه:
  - **PATCH** (`x.y.Z+1`): رفع باگ، تغییر جزئی بدون قابلیت جدید
  - **MINOR** (`x.Y+1.0`): افزودن قابلیت جدید سازگار با قبل
  - **MAJOR** (`X+1.0.0`): تغییر ساختاری ناسازگار با نسخه‌های قبلی (مثلاً تغییر schema دیتابیس بدون migration)

### الزام: به‌روزرسانی نسخه بعد از **هر تغییر**
هیچ commit ای که کد رو تغییر می‌ده، بدون بامپ نسخه (حداقل PATCH) در تمام مکان‌های بالا ثبت نمی‌شه.

---

## ۶. فایل زیپ خروجی

- بعد از هر بامپ نسخه، یک فایل زیپ از خروجی نهایی و **قابل نصب مستقیم در وردپرس** باید در **ریشه پروژه** ساخته بشه:
  - نام فایل: `karasu-buyers-club-{version}.zip` (مثلاً `karasu-buyers-club-0.3.1.zip`)
  - شامل فقط فایل‌های لازم برای اجرا (بدون `node_modules`, `src/`, `docs/`, فایل‌های تست) — یعنی خروجی بیلد‌شده و آماده توزیع
  - زیپ قبلی جایگزین/کنار زیپ جدید نگهداری می‌شه بسته به نیاز (پیش‌فرض: فقط آخرین نسخه در ریشه نگه داشته بشه، مگر خلاف آن خواسته بشه)

---

## ۷. Push به GitHub و Release

بعد از **هر تغییر** که نسخه بامپ شده:
1. `git add` + `git commit` با پیام مطابق فرمت `type(scope): description` (طبق GUIDELINES.md بخش ۴)
2. `git push` به شاخه اصلی (یا شاخه فیچر بسته به گردش‌کار تعریف‌شده)
3. ساخت **GitHub Release** با:
   - تگ نسخه: `v{x.y.z}` (مثلاً `v0.3.1`)
   - عنوان Release: همون شماره نسخه + خلاصه یک‌خطی تغییرات
   - پیوست فایل زیپ ساخته‌شده در بخش ۶
   - توضیحات Release شامل فهرست تغییرات (Changelog) این نسخه نسبت به نسخه قبل

**این چرخه (بامپ نسخه → زیپ → commit/push → release) نباید هرگز شکسته یا نادیده گرفته بشه، حتی برای تغییرات کوچک.**

## ۸. خلاصه چرخه کاری استاندارد برای هر تغییر

```
1. چک کامل docs/ (بخش ۱)
2. ثبت/به‌روزرسانی تسک در docs/tasks.md (بخش ۲)
3. ثبت برنامه در docs/implementation-plan.md (بخش ۳)
4. توسعه کد مطابق ARCHITECTURE.md و GUIDELINES.md
5. تست کارکرد
6. اعتبارسنجی قوانین قبل از commit (بخش ۴)
7. ثبت خطاهای احتمالی در docs/DEBUG_LOG.md
8. بامپ نسخه در همه مکان‌های لازم (بخش ۵)
9. ساخت فایل زیپ در ریشه پروژه (بخش ۶)
10. Commit + Push + GitHub Release با زیپ پیوست (بخش ۷)
```
